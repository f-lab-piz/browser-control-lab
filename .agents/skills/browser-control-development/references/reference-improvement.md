# 요구사항과 참고 방식 보완

사용자가 Codex/Aside의 해결 방식을 요구별로 기록·개선하도록 요청한 경우 [참고 방식 보완 루프](../../../../planning/spec-reference-improvement-loop.md)를 읽는다. 루프 설계 요청은 전체 조사 실행으로 간주하지 않는다. 명시적인 실행 요청이 오면 아래 절차를 적용한다.

- 메인이 정본 편집/판단을 맡고 A/B는 두 제품을 분리 조사한다. 독립 리뷰는 Sol6.1 high 새 컨텍스트이며 자기 조사 결과의 승인과 분리한다. 브라우저 사용은 조정하고 개인 탭/원본 번들/WASM을 조사하지 않는다.
- 기존 REQ 전체에 두 제품의 참고 항목을 연결하되 공통 메커니즘은 한 번 작성한다. API 이름만 맞추지 않고 선행조건·관찰/선택·입력/대기·사후판정·실패/부작용을 대응한다.
- 제품/표면/버전과 claim별 문서·새실측·과거실측·추론·미확인을 구분한다. 자체 wrapper나 일반 Playwright를 원본 제품과 자동 동등 취급하지 않는다. 최소 예제의 실행확인/미실행/의사코드 상태를 명시한다.
- 근거 정확성→설계 적용/조합→반례/예제 검증의 전체3사이클을 순차 수행한다. 각 회차 고정 SHA에서 독립 검토하고 메인이 전 후보를 수용/기각/보류해 규범·참고·PLAN/backlog를 함께 갱신한다.
- 중요 수정의 추가 재검토는 회차별 최대2회다. 필수 충돌이 남으면 미완료와 다음 행동을 남기고 끝없는 재시작/완료 위장을 피한다. 사소한 링크·문구 변경에 전체3회를 자동 적용하지 않는다.
- 연결률은 REQ×제품 슬롯, 근거 확인률/실측률/검토율은 revision별 고정 조건×제품 단위를 분모로 사용한다. 부분 확인과 고유 source/claim/run 수를 따로 세고 공통 근거 재사용을 새 실측으로 중복 집계하지 않는다. 문서 조사 완료와 개발 준비 완료도 구분한다. 미확인 자체는 미지원이 아니며 우리 선택의 독립 근거가 있으면 후속 조사로 남길 수 있다.
- 제품·테스트·fixture·빌드 동결을 유지한다. 필요한 새 검증은 설계로 남긴다. 문서 보완 요청만으로 구현·원격 게시·배포·병합하지 않는다.
