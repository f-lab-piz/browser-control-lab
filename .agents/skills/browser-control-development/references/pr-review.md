# 독립 PR 리뷰 규칙

## 시작과 역할
- 기본 모델: `gpt-6.1-sol`, reasoning `high`. 사용자가 모델을 지정하면 그 지정을 따른다. 해당 모델을 사용할 수 없으면 조용히 다른 모델로 대체하지 않고 알린다.
- 서브에이전트는 새 컨텍스트(`fork_turns: none`)로 시작한다. PR URL, 작업 경로, 정확한 base/head SHA, 프로젝트 스킬, 요구사항, 재현 명령과 결과 형식만 전달한다. 작성자의 예상 문제·결론·원하는 승인 여부를 주입하지 않는다.
- 정식 최초 리뷰와 새 head의 정식 재리뷰는 매번 새 에이전트를 생성한다. 이전 리뷰어에 follow-up만 보내 최종 재승인을 대신하지 않는다. 같은 리뷰 진행 중 질문·재현 보충·보고서 정리는 기존 리뷰어와 이어갈 수 있다. 최근 N턴이나 작성자 대화 요약을 자동 전달하지 않고, 위의 한정된 검토 자료를 요청문으로 전달한다.
- 시작 시 head SHA와 로컬 소스 일치 여부를 확인한다. 리뷰 중 head가 변경되면 검토한 버전과 추가 확인이 필요한 범위를 구분한다.
- 리뷰어는 제품 코드·테스트·문서를 수정하지 않는다. 재현용 scratch와 테스트 결과는 ignored output/ 또는 .local/에만 쓴다. PR 댓글·리뷰 게시·승인·병합은 별도 사용자 지시 없이는 수행하지 않는다.

## 확인할 범위
- 실제 base→head diff와 연결된 코드·테스트·요구사항을 확인한다. PR 제목/본문/기존 PASS 보고서는 주장으로 취급하고 필요한 검증을 직접 한다.
- 입력 없이 성공 반환, 잘못된 대상/프레임 조작, stale/중복 매칭, 실제 가림/readonly/disabled, 파일/세션 경계를 우선 본다.
- snapshot의 역할·이름·상태·대상·프레임·생략 및 후속 조회가 정확한지, 검색과 조작이 같은 의미 체계를 쓰는지 본다.
- 테스트가 판정기를 우회하거나 성공 조건을 완화하지 않았는지, 거절 테스트가 무부작용도 확인하는지 본다. fixture oracle과 제품 확장 결과를 혼동하지 않는다.
- Before/After, Codex/Aside 비교와 결과·버전·소스 해시가 주장과 일치하는지 확인한다. 다른 출력 계약이나 미측정을 성능 우위/성공으로 표현했는지 본다.
- 관련 진단/회귀를 실행하되 제품 동작을 Playwright로 대신하지 않는다. 테스트 수·명령·종료 코드·환경 차단을 기록한다. 실행하지 못한 테스트는 미검증으로 명시한다.

## 발견 사항
각 항목에 P0/P1/P2/P3, 파일·정확한 줄, 구체적 발생 조건, 기대/실제 동작, 사용자 영향과 증거를 포함한다. 실제 재현과 코드 경로로 확인한 사항, 아직 확인하지 못한 가설을 구분한다. 가설은 확정 버그 목록에 넣지 않는다.
- P0: 즉시 중단해야 할 광범위한 데이터 손실/노출 등.
- P1: 이번 범위의 핵심 동작 실패, 잘못된 변경/거짓 성공 등 우선 수정 필요.
- P2: 제한된 조건의 기능 오류·회귀 또는 중요한 검증 누락.
- P3: 비차단 개선.
취향·추측·범위 밖 기능을 버그로 보고하지 않는다. 알려진 제약도 실제 요구 위반이나 안전한 실패 처리 부족이면 근거와 함께 지적한다. 수정 전부터 존재했는지, PR에서 도입/악화했는지 구분한다.

## 결과와 후속 처리
- 보고 순서: 발견 사항 → 검증/재현 명령 및 결과 → 미실행/차단 → 남은 위험 → 검토 SHA와 판정.
- 발견 사항이 없으면 없다고 명시하되 미검증 범위를 생략하지 않는다. 결과를 PASS / CHANGES_REQUESTED / INCOMPLETE로 구분하며 범위가 부족하면 승인을 단정하지 않는다.
- 메인 에이전트는 지적을 확인하고, 수정이 허가된 작업이면 수정 또는 반영하지 않은 근거를 기록한다. 리뷰만 요청받았으면 결과를 보고하고 코드는 그대로 둔다.
- 수정 작업의 완료 조건은 P0/P1 해결, 관련 테스트와 기존 회귀 통과다. 중요한 수정은 같은 모델로 새 head를 재리뷰한다. P2 이하의 보류는 영향과 근거를 명시한다. 재리뷰에서 범위가 달라지면 재검증한다. 병합은 별도 사용자 지시를 따른다.


## 제품 승인 후 문서만 변경된 경우

- 정확한 제품 승인 SHA→최종 head의 diff를 새 리뷰어가 확인한다. 제품·빌드·런타임·테스트·fixture·의존성·설정·도구 안내 등 해당 검증의 모든 실행 입력이 동일하고, 실행 환경/브라우저가 바뀌지 않았으며, 미해결 실패/불안정성으로 재실행할 이유가 없는 경우에 한해 전체 브라우저 suite 대신 문서 delta 검증을 할 수 있다.
- 파일 개수나 확장자만으로 판정하지 않는다. 기록된 fingerprint 목록이 관련 입력을 빠뜨리지 않았는지와 실제 바이트/해시를 확인한다. 실행에 소비되는 가이드·fixture·스크립트는 문서 위치에 있어도 실행 입력이다. 필요한 입력/환경의 동일성을 입증하지 못하면 영향 있는 테스트를 다시 실행한다.
- delta 검증은 승인 제품 SHA/명령/환경/PASS·FAIL·SKIP, 최종 SHA, 입력 동일성, 증거 원시/보존 hash, 문서 일관성, 검사기와 전체 diff-check를 기록한다. 이전 실행을 최종 SHA에서 새로 실행했다고 표현하지 않는다. 머지 gate는 제품 승인과 최종 delta 판정을 함께 사용한다.
- PC/OS/Chrome/의존성 환경이 달라진 재개에서는 과거 PASS를 새 PC의 제품 PASS로 전용하지 않는다. 재개 안내에 따라 먼저 새 환경의 제품 baseline을 실행한다. 브라우저 재실행 생략은 새 PC의 초기 검증을 생략하는 규칙이 아니다.

## 요청과 결과의 보존

- 메인은 리뷰별 agent 식별자, 실제 model/reasoning/fork 설정, 검토 base/head, 범위, 재현/실행 명령, 결과/미실행/남은 위험, 지적별 수용·수정·보류 근거를 구현 보고서 또는 리뷰 기록에 남긴다. 모델/설정이 도구에 없으면 동등성을 꾸며 쓰지 않는다. 기본 모델을 임의 대체하지 않는 기존 규칙을 따른다.
- 다른 PC에서 필요한 최종 리뷰/재리뷰/delta 보고서와 최소 재현 증거는 docs/reviews 및 docs/evidence에 보존한다. output/.local만을 유일한 인계 근거로 삼지 않는다. 현재 PC 원시 경로가 사라지거나 덮어써졌으면 보존 사본·소스 hash·한계를 구분한다. 이 보존은 이전 보고서를 새 리뷰어의 승인 정답으로 전달하라는 뜻이 아니다.
