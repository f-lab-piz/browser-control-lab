# 도구 요구사항 정립과 독립 검토

대상은 기존 외부3개·내부64개다. 공통 규칙은 공통 계약을 참조하고 별칭/관리경로를 새 도구로 자동 합산하지 않는다. 사용자 요청이 범위를 바꾸면 색인과 수를 먼저 갱신한다.

1. 카탈로그·실제 노출·기존 요구/테스트/리뷰를 대조한다. 기준 SHA와 경쟁 문서/실측 날짜·버전·한계를 남긴다. 원본 제품 코드/번들/WASM을 가져오지 않는다.
2. 각 API에 입력·기본값·출력·성공 의미·부작용·오류·범위, 고유 REQ ID, 수준/판단, Given/When/Then, 검증 계획·근거를 작성한다. 코드와 다르다는 이유로 수용된 MUST를 낮추지 않는다.
3. Sol6.1 high 새 컨텍스트로 세 번 **순차** 검토한다. 모델/독립성/원격 게시 제한은 pr-review.md를 재사용한다. 각 회차에 정확한 문서 head SHA와 기준 제품 SHA, 관점, 결과 형식을 전달한다.
   - 1회: 전체 API의 기본 계약·실패·부작용.
   - 2회: Codex/Aside 공개 가이드·실측의 증거 등급, 누락/중복과 조합. 미측정 기능은 미확인이다.
   - 3회: 복잡 프레임/입력/파일/이벤트·키워드 미지 탐색의 반례, 충돌·검증 가능성.
4. 리뷰어는 문서/코드를 수정하거나 원격 게시하지 않는다. 읽은 API 목록과 미검토 범위, 후보별 ID·근거·반례·검증안을 제출한다. 메인은 모든 후보를 수용/기각/보류하고 이유와 변경 ID를 decisions에 남긴다. 갱신을 고정한 뒤 다음 회차를 시작한다.
5. 67개 명세 연결, ID/링크/근거·MUST 검증계획, 세 회차 범위/모든 결정, 미해결 필수 충돌을 검사한다. 구현/검증 갭과 의존성을 개발 backlog에 남긴다. 명세 검사는 제품 E2E PASS가 아니다.

별도 구현 요청이 오면 같은 REQ ID로 실패 테스트·수정·비교를 연결한다. 기존 API나 옵션 계약 변경은 guide/문서·호환성 결정도 함께 다룬다. 3회 검토는 신규 명세 정립 절차이며 모든 사소한 문구 수정에 자동 반복하지 않는다.
