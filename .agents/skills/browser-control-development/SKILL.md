# 개발과 검증

## 구현 경계
- 외부 에이전트 도구는 guide/reset/js 세 개. 공개 내부 API 변경은 docs/toolset.md와 docs/api-catalog.json에 함께 반영한다.
- JS 실행·변수 상태는 확장 내부 런타임에 둔다. 외부 HTTP 중계기는 전송만 하며 Node eval/Playwright 실행으로 제품 엔진을 대신하지 않는다.
- Aside/Codex의 동작·인터페이스를 참고할 수 있으나 원본 코드·추출 번들·제품 WASM은 가져오지 않는다. 범용 라이브러리는 출처와 버전을 기록한다.
- 페이지별 편의 기능보다 공통 프레임·선택·입력·파일 엔진을 공유한다. 중복 API 추가 전에 기존 옵션과 조합을 확인한다.

## 스냅샷
- 관찰은 현재 DOM 전체를 기본으로 한다. viewport 밖의 연결된 요소도 포함하며 스냅샷 생성 때문에 스크롤·클릭·로딩을 일으키지 않는다.
- 가상화·지연 로딩으로 DOM에 없는 데이터를 수집했다고 주장하지 않는다. 프레임, 미수집 영역, 출력 생략과 후속 조회 수단을 표시한다.
- href 전체를 기본 텍스트에 늘어놓지 않고 짧은 표시·ref·요청 시 속성 조회로 연결한다. 필수 역할·이름·상태와 작업 대상 접근성을 유지한다.
- stale ref나 다중 매칭 시 임의의 비슷한 요소에 변경 작업을 하지 않는다. 중첩·교차 출처·OOPIF·Shadow DOM의 실제 접근 경로를 검증한다.

## 개발 순서
변경할 API 계약과 실패 조건을 먼저 정의한다. 최소 단위 검증 후 기본 fixture, 복잡 fixture, 확장 경로 E2E 순으로 검증한다. 전체64 API를 구현한 것으로 표시하지 말고 catalog의 status를 실제 증거에 따라 갱신한다.
상세 시나리오와 판정 기준은 `../../../docs/testing.md`를 읽는다. 구조·호출 계약은 `../../../docs/architecture.md`를 읽는다.

## 검증 등급을 혼동하지 않는다
- `npm test`: 서버 판정기와 문서/API 계약 검증.
- `npm run test:fixtures`: 테스트 사이트 자체의 작동 여부 확인. Playwright 직접 동작이 허용되지만 제품 확장이 통과한 증거는 아니다.
- 제품 E2E는 HTTP → 확장 → 내부 런타임 → 브라우저 조작 경로를 사용한다. Playwright는 브라우저 기동/확장 로드/독립 판독/아티팩트 수집에 사용하고, 제품이 해야 할 클릭·입력·스크롤·드래그를 대신 수행하지 않는다.
- 사이트의 판정 API/내부 JS 상태를 직접 바꾸거나 page.evaluate로 PASS를 주입해 성공 처리하지 않는다. 실제 관찰과 입력으로 업무 완료 조건을 만족시킨다. evaluate 자체 API 검증은 별도 격리 케이스에서 수행한다.
- 결과는 테스트 사이트의 서버 판정, 실제 UI 상태와 실행 추적을 함께 확인한다. HTTP 200이나 예외 없음만으로 성공 판정하지 않는다.
- 네이버 등 외부 사이트는 읽기 탐색으로 별도 검증한다. 변화하는 외부 페이지 결과와 결정적 fixture 결과를 분리한다. 회사 사이트 접근은 실제 접근 가능한 환경에서만 검증했다고 표시한다.

## 결과 기록
output/ 아래 run별로 API/시나리오·브라우저 버전·seed·시간·PASS/FAIL/SKIP·실패 이유·스냅샷 글자수/바이트/노드수·프레임 목록·입력 trace·필요 스크린샷을 기록한다. 별도 프로필만 사용하며 실제 사용자 프로필·인증 파일은 Git에 넣지 않는다. 미구현·환경 차단·검증 실패를 통과로 표현하지 않는다.

## 사용자 요구와 평가 모드
전체 요구는 [개발 요구사항](../../../docs/development-requirements.md), 진단 실행은 [평가 계획](../../../docs/evaluation-plan.md)을 읽는다. 사용자 요청이 평가/비교/개선안 제시라면 그 요청 동안 `extension/`, `bridge/`, 런타임·빌드 엔진은 고정한다. 테스트 사이트·테스트 하니스·문서만 바꾸고, 발견한 실패는 수정 대신 재현 절차·영향·우선순위로 제시한다. 이후 구현은 별도 요청 범위에서 진행한다.

- 64개 API에 대해 호출 가능/성공 assertion/실패 경계/복합 업무를 구분해 coverage를 기록한다. 한 함수 호출이나 단순 버튼 통과만으로 모든 옵션 검증을 선언하지 않는다.
- 각 진단은 독립 run과 실제 UI 입력으로 수행하고 서버 기록 또는 읽기 전용 DOM·파일 바이트로 판정한다. 음성 테스트는 원치 않은 부작용이 없었는지도 확인한다.
- 실패한 조건은 일반 Playwright로 fixture 자체가 동작하는지 별도 확인한다. 이 oracle을 제품 PASS로 합산하지 않는다.
- 비교는 같은 fixture·목표·측정 조건을 사용한다. Codex/Aside의 현재 공개 가이드와 실제 호출 결과만 근거로 삼고 원본 구현을 추출하지 않는다. 문서 확인, 실측, 추론, 실행 차단을 구분한다. 서로 다른 출력 계약의 글자 수만으로 성능 우열을 단정하지 않는다.
- snapshot은 작업 대상 발견률·제어 성공·부작용·역할/상태·출력 바이트·예산/부분조회·프레임 누락을 함께 본다. 검색할 키워드를 모르는 단계부터 영역/프레임/스크롤 위치의 단서로 좁히는 흐름도 평가한다.

## 수정 구현과 비교 PR 절차
사용자가 문제 수정을 요청하면 평가 전용 동결을 해제하고 다음 순서로 개발한다.
1. 같은 fixture·목표·판정 기준의 Before 증거를 보존한다. 실패 조건을 느슨하게 바꿔 통과시키지 않는다.
2. 공통 엔진을 수정하고 원래 진단과 기존 복합 업무 회귀를 실행해 After를 측정한다. 거절해야 하는 입력은 오류와 무부작용을 함께 검증한다.
3. Codex 스타일·Aside 스타일·우리 툴을 같은 페이지에서 비교한다. 우리 툴은 Before/After를 병기한다. 버전·범위·출력 크기·대상 발견/제어·상태·제약을 기록하고 실측/문서/차단을 구별한다. 경쟁 도구를 실행하지 못하면 수치를 만들지 않는다.
4. PR에 수정별 Before/After, 재현 명령, 원본 증거의 요약, 회귀 결과와 남은 제약을 포함한다. 기존 평가 PR을 임의로 병합하거나 덮어쓰지 않는다. 사용자 요청에 따라 별도 수정 PR을 만든다.

## 독립 PR 리뷰
PR 리뷰를 요청받으면 [독립 리뷰 규칙](references/pr-review.md)을 읽고 적용한다. 기본 리뷰 모델은 `gpt-6.1-sol`, 추론 강도는 `high`다. 새 컨텍스트로 독립 검토하며 리뷰와 수정을 분리한다. 리뷰 결과에는 문제 유무와 무관하게 검증 범위·실행/미실행 테스트·남은 위험을 포함한다. 리뷰 요청만으로 코드 수정·원격 리뷰 게시·병합을 허가받은 것으로 해석하지 않는다.
