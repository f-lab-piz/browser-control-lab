# 요구사항·참고 방식 문서 보완 루프

> 아래는 당시 루프 설계 기록이다. 이후 사용자의 실행 지시를 받아 [실행 산출물](../docs/requirements/reference-methods/README.md)을 작성 중이다. 아래의 설계 단계/미실행 문장은 당시 시점이며 실행 기록과 구분한다.

2026-11-01. 설계 기준 문서 head `a06b397bf5e79e1a57b76f90f3b73d6fefa5ce63`, 제품 기준 `700a6a06af3f97729327afaf9becb4ee29bb475b`.

이 문서는 **앞으로 실행할 보완 루프의 설계**다. 이번 설계 검토를 전체 참고 조사3회 실행으로 세지 않는다. 기존 요구184개/외부3·내부64 API/공통5문서를 출발점으로 한다. 이후 수용된 요구가 늘면 실제 ID 집합으로 분모를 다시 계산한다.

## Problem

현재 요구사항과 근거 레지스트리는 있지만, 각 요구를 Codex/Aside에서 어떤 공개 API와 호출 조합으로 해결하는지 연결이 부족하다. 기능 이름만 대응하거나 과거 실측을 현재 지원으로 일반화하면 다음 구현에서 잘못 참고할 수 있다. 모델이 같은 주장을 반복 승인하는 루프와 끝없이 요구를 늘리는 루프도 피해야 한다.

## Target User

요구사항을 구현할 메인 개발 에이전트, 비교 근거를 조사하는 서브에이전트, 독립 검토자다. 사람이 각 요구의 근거·설계 판단·검증 방법을 이어서 읽을 수 있어야 한다.

## User Value

REQ ID에서 두 제품의 확인된 해결 방법, 적용할 설계 선택, 확인되지 않은 부분과 테스트 계획을 함께 확인한다. 공통 메커니즘은 재사용하고 서로 다른 제품의 제약·출력 계약을 무리하게 통일하지 않는다.

## Use Cases

1. filter 개발 전에 본문/접근 이름·공백·정규식의 각 조건과 경쟁 API 조합·반례를 읽는다.
2. snapshot 개발 전에 offscreen/iframe/생략/부분조회/ref 수명과 키워드 미지 탐색의 참고 방법을 확인한다.
3. 다운로드 이벤트→실제 저장→서버 asset→업로드처럼 여러 도구 조합으로 해결할 요구를 연결한다.
4. 경쟁 도구의 방식과 다른 우리 정책을 유지할 때 이유와 수용 기준을 보존한다.
5. 근거가 없는 항목은 미확인으로 표시하고 다음 조사나 자체 검증 계획으로 연결한다.

## Corner Cases

공개 가이드만 존재하는 옵션, 실행 차단, 과거 버전 실측, 현재 문서와 관측 충돌, 같은 이름/다른 의미 API, 원본 제품과 자체 wrapper 혼동, 특정 요구만 부분 충족하는 호출 예시, 합성 예제의 미실행, 지연 로딩/프레임/세션·파일 경계, 여러 요구에 같은 메커니즘을 재사용하는 경우를 다룬다.

경쟁 도구에 같은 이름의 API가 없다는 사실은 기능을 조합해 해결할 수 없다는 증거가 아니다. 자료에 없는 기능을 미지원으로 단정하지 않는다. 접근 가능한 동작·공개 계약을 참고하며 원본 코드·추출 번들·제품 WASM은 수집하지 않는다.

## Behavior Spec

### 1. 범위와 동결

- 요구사항·참고 방식·근거·검증 계획·판단 기록·backlog·프로젝트 스킬만 보완한다.
- 제품, 테스트 사이트, 테스트/빌드 원본은 이번 문서 루프에서 고정한다. 신규 fixture가 필요하면 설계와 조사 계획만 남긴다.
- 기존 fixture에서 필요한 비교 관찰은 가능하다. 제품 수정 없이 ignored scratch에 최소 호출/판독 결과를 남긴다. 우리 엔진 테스트가 아니면 우리 제품 PASS로 세지 않는다.
- 테스트 프로필/fixture 탭만 사용한다. 회사/개인 사이트의 변경·원격 게시·push/PR·병합은 이 루프에 포함하지 않는다.
- 이번 요청은 루프 설계까지다. 아래3사이클 실제 실행 기록은 향후 실행 시 별도 생성한다.

### 2. 역할과 동시 작업

|역할|책임|작성 권한|
|---|---|---|
|메인|REQ 분할·자료 배정, 두 조사 결과 통합, 반례 확인, 모든 제안 판단, 규범/참고/매핑 갱신과 완료 판정|정본 문서의 유일 편집자|
|조사 A|Codex의 해당 요구별 공개 안내·API·기존/새 관측 확인, 해결 흐름·지원 한계·반례 제안|자기 ignored 조사 산출물만|
|조사 B|Aside의 같은 항목 조사; 기존 wrapper와 원본 제품/CLI를 구분|자기 ignored 조사 산출물만|
|독립 리뷰 C|고정된 갱신본을 새로운 컨텍스트에서 검토; 출처를 직접 확인하고 후보·검토 범위·한계 제출|자기 ignored 보고서만|

최대 메인+조사2+리뷰1의4개 슬롯 안에서 운영한다. A/B의 문서 읽기는 병렬 가능하다. 브라우저 실측은 메인이 사용권을 배정해 같은 프로필/탭을 동시에 조작하지 않으며 각 run/세션·산출물을 분리한다. 리뷰는 해당 회차 통합본을 고정한 후 시작한다.

독립 리뷰는 프로젝트 규칙대로 **gpt-6.1-sol / high / fork_turns:none**이다. 다음 회차 리뷰는 새 컨텍스트로 시작한다. 조사자가 자기 주장을 최종 승인하는 역할을 겸하지 않는다. 리뷰어에게 작성자의 예상 결론을 주지 않는다. 조사자는 근거와 차이를 보고하고 메인이 채택 여부를 결정한다.

### 3. 배치와 전체 범위

기존 B01~B06의 여섯 개발 묶음과 공통 계약을 조사 배치로 재사용한다: 실행/출력, 선택/검색, snapshot/frames/capture, 상태/입력, 파일/이벤트, 수명/대기/평가/로그. 각 요구는 책임 배치 하나와 필요한 공통 메커니즘 링크를 가진다.

모든 요구에 **Codex와 Aside 각각**의 참고 항목을 연결한다. 초기 연결 슬롯은184×2=368개지만, 같은 메커니즘을 여러 요구에 중복 서술하지 않는다. 368개가 모두 새 실측을 의미하지 않으며 자료가 없는 슬롯도 명시 상태로 관리한다.

각 사이클은 여섯 배치 전체를 다룬다. 대표 snapshot/filter만 보고 전체184개 검토로 보고하지 않는다. 실제 읽은 REQ/참고 항목과 미검토 목록을 남긴다. 자원 제한이 있으면 배치를 순차 처리하고 빠진 범위를 완료 전에 보충한다.

### 4. 문서와 데이터 구조

실행 시 만들 산출물:

```text
docs/requirements/reference-methods/

  index.json                 REQ → 양쪽 참고 항목·설계 판단·검증 연결
  runtime-output.md          공통 메커니즘 정본(이하 배치별6개)
  selection-search.md
  snapshot-frames.md
  input-state.md
  files-events.md
  lifecycle-evaluation.md
  evidence-index.json        claim/source/run·버전·범위
  decisions.md               참고 방식 채택·수정·유지·보류 판단
  coverage.json              연결/근거/검토/미확인 상태를 구분한 집계
  reviews/cycle-N/
    review.md
    decisions.md
```

원본 요구의 규범/GWT는 기존 Markdown에 유지한다. 각 REQ 단락에는 관련 참고 항목 링크만 추가하고, 공통 메커니즘 설명·예제를 복사하지 않는다. reference index는 매핑/상태만 담고 규범이나 긴 방법 본문을 중복하지 않는다. 메커니즘 정본은 실제 충족한다고 주장하는 REQ 집합을 명시하고 요구마다 적용 차이/누락 조건을 덧붙인다.

### 5. 참고 항목의 필수 내용

|필드|규칙|
|---|---|
|식별|REF ID, 연결 REQ ID들, 적용 범위(전체/일부 조건), 담당 배치|
|제품·표면|Codex CUA/in-app browser/자체 Codex-style bridge, Aside 원본 CLI/자체 wrapper 등 정확한 표면. 일반 Playwright 문서와 자동 동등 취급 금지|
|해결 관계|직접 API / 여러 API 조합 / 대응 개념 없음 / 미확인. 대응 개념 없음도 범위·이유·조합 검토 근거 필수|
|해결 흐름|선행 조건→관찰→탐색→입력/대기→결과 확인. 정상·경계/실패·허용 부작용·복구를 관련 REQ 조건과 대응|
|호출 예시|공개 문법으로 작성한 최소 예제. 실행확인/문법확인만/미실행예제/의사코드를 구분. 모르는 API를 그럴듯하게 만들어 넣지 않음|
|근거|claim별 source ID·정확한 절/위치·확인일·제품/브라우저 버전·fixture/run. 문서/새실측/과거실측/추론/근거없음을 각각 구분|
|지원 경계|어느 옵션/조건까지 확인했는지. 자료 없음·실행 차단은 미지원 아님. 상반된 문서/관측은 둘 다 보존하고 충돌 이유 기록|
|우리 판단|그대로 채택 / 조정 채택 / 우리 방식 유지 / 보류 / 기각과 이유. 현재 구현 사실과 다음 구현의 선택을 구분|
|검증 연결|REQ의 PLAN ID, 정상/거절/무부작용·부분효과 판정, 부족한 fixture/조사·우선순위|

근거의 단위는 문서 전체가 아니라 **개별 주장**이다. 한 API의 정상 호출을 실측했다고 옵션/경계/복합 업무 전부를 실측으로 올리지 않는다. 가이드를 읽어도 구현 내부 알고리즘을 알아냈다고 서술하지 않는다. 작은 코드 예제는 사용법을 독자적으로 작성하며 경쟁 제품의 구현 소스를 복사하지 않는다.

### 6. 비교 슬롯의 상태

해결 관계와 근거 종류를 별도 필드로 둔다. 여러 근거를 한 슬롯에서 사용할 수 있지만 claim별 구분은 유지한다.

- 근거 종류: DOC(가이드), LIVE(해당 run 실측), HISTORICAL(이전 버전/회차 실측), INFERENCE(명시 추론), NONE(자료 없음).
- 확인 상태: 조사완료(기록한 범위에 한정) / 미확인 / 실행차단. 차단은 원인·조건·다음 행동을 기록한다.
- 검토 상태: 미검토 / 검토완료 / 수정필요. 검토완료가 제품지원 확인을 뜻하지 않는다.
- 판정은 별도다: 동일 목표 충족 / 일부 충족 / 의도된 차이 / 확인 불가. 확인되지 않은 미지원·성공 판정을 생성하지 않는다.

**연결률**, **근거 확인률**, **실측률**, **독립 검토율**을 나누어 보고한다. 미확인으로 채운368개 슬롯은 연결률만100%일 수 있다. 그것을 비교 조사100%나 개발 준비 완료라고 쓰지 않는다.

### 6-1. 집계 단위와 부분 확인

각 revision에서 규범/GWT를 관찰 가능한 조건으로 분해한 conditionKey 목록을 고정한다. 이는 참고 조사용 추적 키이며 정본 규범을 복제하거나 새 REQ를 자동 생성하는 절차가 아니다. 집계 단위는 `(REQ ID, conditionKey, 제품 표면)`이며 제품 표면은 두 비교 대상에서 정확히 고정한다. 공통 REQ의 조건은 정본 ID에서 한 번 분해하고 각 API에 상속된다고 분모를 재복제하지 않는다.

- **연결률:** 연결된 `(REQ, 제품)` 슬롯 수 / 해당 revision의 전체 REQ×2. 초기184개면368슬롯이다.
- **조건별 근거 확인률:** 직접 근거가 해당 조건 전체를 뒷받침하는 단위 수 / 같은 revision의 전체 조건×2. DOC/LIVE/HISTORICAL 비율을 각각 제시하고 INFERENCE/NONE/상충 미해결은 확인 분자에 넣지 않는다. 같은 단위에 근거가 여러 종류이면 종류별 비율은 겹칠 수 있으므로 합산하지 않는다. 통합값이 필요하면 합집합으로 센다.
- **실측률:** LIVE가 뒷받침하는 조건 단위 수 / 전체 조건×2. HISTORICAL은 별도로 보고한다. LIVE도 run에 기록한 버전·fixture·조건 범위에 한정하며 현재 모든 환경 지원을 의미하지 않는다.
- **독립 검토율:** 고정 검토 SHA에서 실제 읽고 판단한 조건 단위 수 / 그 SHA의 전체 조건×2. 조건 하나라도 미검토면 해당 슬롯을 전체 검토로 세지 않는다. 검토 뒤 내용이 바뀐 조건은 변경분/재검토 여부를 따로 표시한다.

부분 확인은 조건별로 남긴다. 예컨대 한 요구의4조건 중1조건만 DOC로 확인했다면 그 슬롯은 부분 확인이고 조건 DOC 범위는1/4다. 같은 REF/run을 여러 요구에서 재사용하면 해당 조건의 연결은 여러 건일 수 있지만 **고유 source/claim/run 수**를 별도로 중복 제거해 보고한다. 두 요구가 같은 실측 run을 참조해도 새 실측2회라고 세지 않는다. source URL이 있다는 이유만으로 조건을 확인했다고 세지 않는다.

정말 대응이 없는 조건도 분모에서 조용히 빼지 않고 이유·판단을 별도 표시한다. 조건/요구가 추가·삭제되면 이전/이후 분모와 변경 이유를 함께 보고해 단순 비율 상승을 개선량으로 단정하지 않는다. 이 집계 정의를 구현하는 JSON/검사기는 실제 루프 실행 시 문서 도구로 준비하며 이번 설계 단계에서 제품 코드를 추가하지 않는다.

### 7. 세 사이클

#### 1회 · 근거와 대응 방식

1. 메인이 기준 SHA·REQ 집합·기존 source/evidence를 고정하고 각 배치에 A/B 조사를 배정한다.
2. A/B가 공개 가이드/기존 실측을 우선 재사용하되 날짜·범위를 검증한다. 새 실측은 판단에 중요한 공백 중 기존 fixture로 확인 가능한 경우에 한정한다.
3. 메인이 공통 메커니즘과 REQ별 차이를 통합하고, 참고 슬롯/자료 없음/실행차단을 채운다.
4. 통합본을 커밋으로 고정한다. C가 출처 오인·API 문법·전체/부분 적용·미검토·허위 지원을 검토한다.
5. 메인이 후보별 수용/기각/보류와 이유·변경 REF/REQ/PLAN을 기록하고 갱신본을 고정한다.

완료 결과: 빈 슬롯/고아 ID 없음, 두 제품 표면 구분, 모든 사실 주장에 직접 출처 또는 명시 미확인/추론. 새 실측 수를 강제하지 않는다.

#### 2회 · 설계 적용과 요구 개선

1. A/B는1회 갱신본을 기준으로 단일 도구가 아닌 조합·실패/복구·중복 API 대안을 교차 검토한다. 서로의 산출물을 이때 열어 비교할 수 있다.
2. 메인은 기존 요구가 누락/모호/과도한지 판단한다. 경쟁사가 한다는 이유만으로 MUST나 도구를 추가하지 않는다. 사용자 업무·반례·비용·기존 조합 가능성으로 결정한다.
3. 수용된 수정은 기존 ID를 유지하고 의미 변경·새 요구는 이력을 남긴다. 새로운 요구는 고유 ID·GWT·근거·참고 슬롯·backlog 연결을 함께 만든다. 제품/카탈로그를 구현 완료 상태로 바꾸지 않는다.
4. 새 고정 SHA를 C의 새 컨텍스트로 검토한다. C는 설계 판단 근거·규범 충돌·차이의 정당성·범위 확대를 반박 검토한다.
5. 메인이 모든 후보를 판단하고 규범/참고/검증/의존 관계를 동시에 갱신한다.

완료 결과: 참고 방식 채택 여부의 근거, 의도된 차이, 불필요한 확장 보류, 수용된 모든 요구의 구체적 검증 계획.

#### 3회 · 반례·예제·실행 가능성

1. A/B가 인접/긴 텍스트·슬롯·중첩/OOPIF·overlay·virtual scroll·stale·이벤트경합·파일바이트·reset/출력 한도에서 참고 흐름을 점검한다.
2. 목표 이름/selector를 모르더라도 공개 업무 predicate로 발견 가능한지, 관찰의 무스크롤과 명시 입력의 효과가 분리되는지 확인한다. 식별 불가능한 숨은 정답 과제를 쓰지 않는다.
3. 최소 예제의 API/버전/선행 조건·미실행 표지를 확인한다. 직접 실행할 수 없는 새 fixture는 검증 설계로 남기고 제품 PASS를 만들지 않는다.
4. C의 새 컨텍스트가 모든 배치의 최종 주장·미확인·GWT·추적을 검토한다. 메인이 전 후보를 판단·갱신한다.
5. 메인이 ID/링크/근거/범위/부작용/매핑과 제품 동결을 검사하고 종료 보고한다. 마지막 메인 갱신을 독립 리뷰어가 승인했다고 표현하지 않는다.

완료 결과: 모든 REQ에 실제 구현 시 참고할 수 있는 흐름 또는 명시된 자료 공백·우리 자체 근거/검증 계획이 있고, 알려진 필수 규범 충돌·판정 불가 표현이 남지 않는다.

### 8. 종료·재검토·중단 기준

기본은 전체3회다. 새 지적을 만들거나 모두 수용하도록 강제하지 않는다. 각 후보에는 근거와 결정 이유가 있어야 한다. 단순 오탈자와 링크 수정은 메인의 구조검사로 끝내고 의미 변경/중대한 근거 오류는 해당 부분을 새 컨텍스트로 재검토한다.

각 회차에서 중요한 수정의 추가 재검토는 최대2회로 한정한다. 그래도 필수 충돌/검증 불가능한 목표가 남으면 해당 항목을 미완료로 표시하고 원인·영향·필요 정보·다음 행동을 보고한다. 무한 반복하거나 MUST를 낮춰 완료로 포장하지 않는다. 전체 세 회차를 다시 시작하지 않는다.

종료 보고는 두 수준을 구분한다.

- **문서 조사 루프 완료:** 전체 범위/세 회차/모든 후보 판단·출처·매핑을 기록했다. 미확인·차단도 숫자와 목록으로 공개한다.
- **개발 준비 완료:** 위 조건에 더해 우리 MUST의 선택 이유·검증 계획이 있고 필수 설계 충돌이 없다. 경쟁 방식 미확인만으로 개발을 자동 차단하지는 않지만, 확인되지 않은 경쟁 지원에 의존한 필수 설계는 해결 전까지 미완료다.

경쟁 제품 내부 구현을 모르는 항목을 억지로 채우는 것은 종료 조건이 아니다. 이번 개발 판단을 바꾸지 않는 비교 공백은 근거를 남겨 후속 조사로 보낼 수 있다. 미지원/의도적 차이·미확인/차단을 섞지 않는다.

## Cost and Complexity

184개 요구×양쪽 슬롯, 여섯 공통 배치, 세 독립 검토와 매번의 메인 판단이 필요하다. 실행 비용은 문서 조사보다 브라우저·파일·이벤트 경계 실측이 크다. 한 항목마다 같은 예제를 복사하거나 전부 새 실측하면 비용과 관리 부담이 커진다.

낮은 비용 대안은 기능군별 비교표 하나와 단일 리뷰다. 파악은 빠르지만 REQ별 부분조건/반례 누락을 추적하기 어려워, 이번에는 공통 메커니즘 정본+REQ별 얇은 연결을 채택한다. 이미 유효한 근거를 재사용하고 판단에 중요한 공백만 먼저 측정한다. 근거 없이 일정을 약속하지 않는다.

## Usability

개발자는 REQ→참고 항목→공개 호출/조합 예제→근거·한계→우리 선택→PLAN/backlog 순서로 읽는다. 깊은 원시 로그는 근거 레지스트리에 연결하고 본문에는 판단에 필요한 결과를 둔다. 문서/실측/추론과 구현·검증 상태가 한눈에 구별되어야 한다.

|조사자가 자기 주장을 승인|정본 메인 편집+새 컨텍스트 독립 C|

## Decision

두 제품 조사 A/B, 메인 통합·판단, 독립 리뷰 C의 역할을 분리한 전체3사이클을 사용한다. 같은 메커니즘은 공통 정본에 두고 모든 REQ가 양쪽 참고 항목에 연결되도록 한다. 현재 단계는 이 루프의 설계·독립 검토이며 전체 비교 조사 실행은 후속 단계다.

## MVP Scope

기존184개 요구와 기존3+64 API/공통 계약. 공개 API·가이드·기존 증거·기존 fixture에서 필요한 추가 관찰, 참고·검증·판단 문서의 보완이다. 신규 제품 구현, 테스트 사이트 고도화, 사내 실환경 실행, 배포/원격 GitHub 작업은 자동 포함하지 않는다.

## Success Metrics

- 실제 REQ 집합과 참고 index 일치, 양쪽 슬롯 누락/고아0. 초기368슬롯이나 요구 변경 시 재계산.
- 사실 주장에 출처/범위/확인일 또는 명시 미확인·추론 연결100%.
- 참고 항목의 호출 예제 상태·적용 조건·우리 판단·PLAN 연결100%.
- 전체3회 독립 검토와 실제 검토 범위/모든 후보 판단 기록. 최종 메인 갱신의 독립 승인 여부는 별도 표기.
- 완료 보고에 확인/미확인/차단·미완료 수치를 분리. 미해결 필수 충돌을 숨긴 완료0.
- 제품·테스트·fixture·빌드 원본 변경0. 단순 요구 증가/신규 실측 개수는 성공 지표가 아니다.

## Open Questions

현재 접근 가능한 Codex/Aside 표면의 최신 버전과 문서/실측 가능 범위는 실행1회차에서 확인한다. 기존 fixture로 판정할 수 없는 요구는 새 fixture 설계가 필요할 수 있으나 이 문서 루프에서 구현하지 않는다. 이 불확실성은 설계를 막지 않으며 실행 결과의 상태로 관리한다.

## Next Actions
