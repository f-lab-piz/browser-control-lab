# 도구별 요구사항 정립과 3회 독립 검토 계획

2026-11-01. 계획 기준 main: `700a6a06af3f97729327afaf9becb4ee29bb475b`.
현재 단계는 계획 작성이다. 이 문서는67개 명세 작성·검토3회·제품 개발을 이미 수행했다는 의미가 아니다.

## Problem

현재 요구사항이 toolset, 개발 계약, API 카탈로그, 테스트, 과거 비교·리뷰 보고서에 나뉘어 있다. 일부 문서는 당시 상태를 기록해 현재 구현과 다르다. 기본 호출·진단이 통과해도 인라인 텍스트·summary Shadow DOM·스크롤 clip 같은 조합 조건이 뒤늦게 발견됐다. API별 규범, 구현 상태, 검증 증거를 분리하고 서로 연결할 필요가 있다.

## Target User

브라우저를 제어하는 에이전트, 툴을 구현·검증하는 개발 에이전트, 독립 리뷰 서브에이전트다. 최종 사용자의 업무를 정확한 대상으로 수행하고 실패·생략을 이해할 수 있는 계약을 제공한다.

## User Value

- 어떤 동작을 보장해야 하는지 구현 전에 확인한다.
- 실패 사례를 해당 API의 지속적인 요구와 회귀 테스트로 남긴다.
- 경쟁 도구에서 참고할 조건과 우리 제품에서 실제 필요한 조건을 구분한다.
- 테스트 PASS를 전체 옵션/모든 사이트 지원으로 과대 해석하지 않는다.

## Use Cases

1. 개발자가 locator.filter를 수정하기 전 텍스트·공백·정규식·숨김·범위 의미와 거절 조건을 확인한다.
2. 에이전트가 키워드를 모르는 페이지에서 구조→영역/프레임→대상 탐색→제어로 이어간다.
3. 실패를 발견하면 요구사항 ID·반례·재현·테스트를 연결한다.
4. Codex/Aside의 현재 문서·실측을 검토해 후보를 만들고 수용 여부를 기록한다.
5. 요구사항 확정 후 부족한 테스트와 구현을 우선순위에 따라 개발하고 같은 조건으로 재리뷰한다.

## Corner Cases

중복·낡은 ref, DOM/프레임 교체, 인접/긴/Unicode 텍스트·실제 공백, slot/open Shadow DOM, 닫힌 details, 내부/가로/가상 스크롤, OOPIF와 transform, readonly/disabled/가림, 캡처 중 viewport 변경, 이벤트 순서·취소·시간초과, 파일 바이트·로컬/서버 경계, 결과 예산·부분조회·미로드 데이터를 다룬다.

브라우저·권한·접근 제한으로 불가능한 조건은 성공으로 꾸미지 않고 지원 범위·명시적 오류·미검증으로 구분한다. 전체 웹/전 브라우저의 무조건 지원을 필수 조건으로 쓰지 않는다.

## Behavior Spec

### 1. 범위와 파일 구조

외부 guide/reset/js3개와 내부 공개 API64개를 각각 문서화한다. Page/Frame 공통 Scope는 별도 중복 계산하지 않는다. 카탈로그와 실제 노출 표면의 불일치는 먼저 조사하며, 숨은 별칭을 발견했다고 자동으로 신규 API를 추가하지 않는다.

예정 구조:

```text
docs/requirements/
  README.md                  읽는 순서·용어·상태 정의
  index.json                 3+64 API → 고유 명세 경로·ID 연결
  sources.md                 근거와 버전·날짜·범위·실측 방법
  common/
    runtime.md               세션·실행·출력·reset·제한
    dom-frames.md            현재 DOM·프레임·Shadow·미수집 경계
    selection.md             텍스트·역할·ref·엄격 매칭
    input.md                 좌표·상태·부작용·실패 의미
    files-events.md          파일·이벤트·취소·소유 경계
  external/{guide,reset,js}.md
  internal/{scope.snapshot,locator.filter,...}.md
  verification-matrix.json   요구사항ID → 정상/거절/복합 테스트·증거
  reviews/
    cycle-1/{review,decisions}.md
    cycle-2/{review,decisions}.md
    cycle-3/{review,decisions}.md
```

개별API 명세는67개이며 공통 문서·색인·근거·검토 기록은 추가다. 위 디렉터리는 계획일 뿐 이번에 빈 명세67개를 생성하지 않는다.

### 2. API별 명세 양식

- 식별: API 이름, 적용 객체/프레임 범위, 공통 계약 참조.
- 목적·사용 사례·이번 버전의 지원 범위.
- 입력: 타입·기본값·정규화·옵션 조합·잘못된 입력의 처리.
- 출력: 반환 타입·결과 의미·메타데이터·생략과 후속 조회.
- 동작: 정상 조건·선행 상태·업무 효과와 부작용, 필요 시 원자성/부분 완료.
- 오류: 구분 가능한 실패, 중복/낡은 대상, 제한·취소·권한, 재시도 가능 여부.
- 경계: 공통 계약과 해당 API 고유 조합/반례.
- 검증: Given/When/Then, 성공·거절·무부작용·복합 업무, 외부 환경 조건.
- 근거와 판단: 기본 설계 제안, 사용자 요구, 개발 중 발견, Codex/Aside 문서/실측.
- 현재 충족 상태와 증거. 미검증을 미구현/실패와 섞지 않는다.

모든 항목에 같은 수의 규칙을 채우지 않는다. 적용하지 않는 항목은 이유를 기록한다. 공통 조건은 복사하지 않고 공통 ID를 참조한다.

### 3. 요구사항 단위 메타데이터

| 필드 | 내용 |
|---|---|
|ID|예: REQ-FILTER-001. 삭제해도 재사용하지 않음|
|규범|관찰 가능한 조건 한 개. 여러 독립 조건은 나눔|
|수준/대상 버전|이번 개발의 MUST / SHOULD / 후속 후보|
|근거|source ID·날짜·버전·조건; 사실/제안/추론 구분|
|판단|초안 / 수용 / 기각 / 보류, 이유·결정 사이클|
|충족 상태|충족 / 부분 충족 / 미구현 / 미검증 / 해당 없음|
|검증|test ID·환경·정상/거절/부작용 판정·결과 증거|

요구사항 규범의 원본은 API/common Markdown이다. index와 matrix는 매핑/상태를 담으며 본문을 중복 복사하지 않는다. 결정 상태와 구현 상태를 분리한다. 수용된 MUST가 현재 구현되어 있지 않아도 규범을 낮춰 맞추지 않는다.

예시 방향(실제 명세 작성 시 근거·ID 확정):
- filter: 인접 `<span>foo</span><span>bar</span>`에 없는 공백을 삽입하지 않고 양/음 필터가 각각1/0을 반환한다. 실제 DOM 공백은 구분한다.
- snapshot: 관찰 때문에 스크롤/추가 로딩을 일으키지 않고 현재 DOM의 화면 밖 대상을 후속 조회할 수 있다. 예산 생략과 DOM 미존재를 구별한다.
- reset: 실행/변수를 초기화하더라도 이미 발생한 웹 업무를 되돌렸다고 반환하지 않는다.

### 4. 작성 순서와 근거 수집

1. 기준 커밋·API 수·실제 노출 표면과 기존 문서/테스트를 대조한다. 오래된 상태 설명은 당시 기록으로 표시하고 현재 사실과 구분한다. ideation 폴더는 현재 없으므로 기존 사용자 요구·개발 문서·리뷰를 출발점으로 한다.
2. 공통 계약과 양식을 먼저 정한다.
3. snapshot·프레임·선택·필터·입력 등 오류 영향이 큰 API부터 작성하고 파일/이벤트, 브라우저/탐색, 런타임/출력을 완성한다. 모든67개를 색인으로 확인한다.
4. Codex/Aside의 그 시점 사용 가능한 가이드·문서·fixture 실측을 근거 목록에 기록한다. 기존 비교 기록은 버전/당시 조건의 사실로 보존한다. 외부 실행이 차단되면 비교 미검증과 후보를 남긴다.
5. 범용 기능의 조합을 먼저 검토한다. 새 외부 도구/사이트별 전용 기능을 요구사항 정리의 부산물로 늘리지 않는다.

### 5. 세 번의 독립 검토와 갱신

각 회차는 `gpt-6.1-sol`, high, 새 컨텍스트(fork_turns:none)로 수행한다. 리뷰어는 요구사항·근거·현재 드래프트의 고정 버전과 검토 기준을 받는다. 원하는 결론이나 작성자의 예상 추가 조건은 전달하지 않는다. 리뷰어는 규범 원본을 수정하거나 구현하지 않고 제안과 증거를 제출한다. 개발 리뷰 규칙의 독립성·미검증 보고 원칙을 재사용하되 이 단계의 대상은 요구 명세다.

| 회차 | 검토 관점 | 필수 산출물 |
|---|---|---|
|1차: 기본 계약|67개 API 목적·입출력·거절·부작용·공통 계약 누락/모순|API별 검토 범위표, 후보·반례·검증 제안|
|2차: 비교와 조합|Codex/Aside 문서·실측과 대조, 필요한 조건 누락, 불필요한 확장·중복|근거별 차이, 실측/문서/차단 구분, 후보|
|3차: 반례와 실행 가능성|복잡 조합·키워드 미지 탐색, 명세 충돌·비검증 문장, 테스트 가능성/범위|최종 누락·충돌·비검증 목록과 검증 설계|

매 회차 뒤 메인 에이전트가 후보를 하나씩 수용/기각/보류하고 근거·중복 여부·변경한 ID를 decisions.md에 기록한다. 수용하면 규범과 매핑을 갱신해 다음 회차에 전달한다. 요구를 단순히 늘리기 위해 제안을 강제 수용하지 않는다. 추가할 것이 없는 회차도 실제 검토 범위와 이유를 기록하고 예정된3회를 진행한다.

리뷰는 그룹별로 문서를 읽고 범위표를 남긴다. 대표 snapshot/filter만 확인하고 전체67개를 검토했다고 표시하지 않는다. 미검토 API는 명시하고 개발 전환 전 보충한다. 차단된 경쟁 도구의 실측은 만들어 내지 않으며 사용자 요구·공통 계약만으로 판단할 수 있는 부분을 계속한다.

### 6. 명세 완료와 개발 전환

- 67개 API의 고유 명세·공통 참조가 있고 카탈로그 누락/중복/고아 링크가 없다.
- 수용된 모든 MUST가 정상/실패/부작용 중 적용되는 수용 기준 및 검증 계획에 연결된다. 기존 테스트 미존재는 개발 backlog로 명시한다.
- 3회 리뷰와 모든 제안의 결정이 기록되고, 필수 조건의 미해결 충돌·검증 불가능 표현은 개발 전에 해소한다. 해결되지 않는 조건은 근거를 남겨 후보/보류로 분리하며 MUST 완료로 세지 않는다.
- 지원 브라우저·권한·미로드 데이터·출력 예산·조건별 제한이 명시된다. 이 시점은 명세 완료이지 제품 구현 완료가 아니다.
- 수용된 요구 ID별 테스트/구현 갭, 우선순위와 의존성을 정해 별도 개발 계획/PR 단위로 나눈다.

개발은 관찰/선택/입력의 정확성 → 파일/이벤트/런타임 복구 → 나머지 지원 옵션 순을 기본으로 하되 실제 갭/의존성으로 조정한다. 먼저 재현·실패 테스트를 추가하고 구현한다. 같은 조건의 Before/After·회귀·독립 PR 리뷰를 기록한다. 새 요구를 반영할 때 명세와 ID를 갱신한다. 통과시키려고 요구나 기존 판정을 느슨하게 바꾸지 않는다.

## Cost and Complexity

개별67개와 공통 계약 작성, 근거 검증, 검토3회, 결정3회, 매핑 검사가 필요하다. 모두에 전체 지침을 복사하면 유지 비용과 모순이 커지므로 공통 참조·얇은 개별 명세·기계 판독 색인을 사용한다. 시간은 실제 요구 수와 경쟁 도구 접근 상태에 좌우되므로 지금 근거 없는 날짜/시간을 약속하지 않는다.

더 저렴한 대안은 분류별 통합 문서와 단일 리뷰다. 작성량은 작지만 개별 도구의 계약과3회 검토 이력을 원하는 이번 요청에는 채택하지 않는다. 개별 파일을 유지하면서 공통 내용을 공유하는 방식을 선택한다.

## Usability

개발자는 API 색인→개별 규범→공통 계약→검증/결정 기록 순서로 필요한 부분만 읽는다. 요구 ID로 테스트·근거·결정을 양방향 탐색한다. 긴 비교 로그는 근거로 연결하고 규범 본문에는 판단에 필요한 요약만 둔다. guide에 노출할 사용자 계약과 개발 내부 검증 절차를 분리한다.

## Risks and Mitigations

| 위험 | 대응 |
|---|---|
|현재 코드를 규범으로 베낌|목표 규범과 구현/검증 상태 분리|
|경쟁 기능을 모두 MUST로 가져옴|사용 사례·조합 가능성·비용으로 채택 판단, 나머지는 후보/보류|
|과거 문서의 낡은 상태를 현재 사실로 사용|커밋·날짜·버전·증거 계층 명시|
|67개와 공통 규칙의 중복/충돌|고유ID·공통 참조·색인/링크 검사|
|3회 검토가 같은 말 반복/승인 의식으로 끝남|회차별 관점·독립 컨텍스트·검토 범위·후보별 결정|
|테스트 종료0/개수만으로 완료 주장|실제 목표·거절·무부작용 assertion과 검증 범위를 연결|
|범위가 커져 개발을 못 시작|이번 버전 MUST와 후속 후보 분리, 우선순위 backlog|
|설명 문서가 실행 가능한 부작용을 허가하는 것으로 오해|fixture 중심 read-only 근거 수집, 원격 게시/삭제/병합 권한은 사용자 요청 범위로 제한|

## Decision

개별 명세67개 + 공통 계약 + 근거 + 검증 매핑 + 독립3회 검토/결정 기록을 만든 뒤 개발로 전환하는 방향을 선택한다. 이번 작업은 계획 작성까지다. 아직 서브에이전트를 실행하거나 툴 코드를 바꾸지 않았다.

## MVP Scope

첫 요구사항 버전의 대상은 기존 외부3개/내부64개다. 모든 API에 계약·범위·오류·수용 기준·근거·상태를 작성하고 필요한 공통 계약을 둔다. 신규 외부 도구, 사이트 전용 기능, 전 브라우저 완전 지원과 상용 배포 구현은 자동으로 포함하지 않는다. 후보가 나오면 결정 기록에서 별도로 판단한다.

## Success Metrics

- API 문서 연결:3/3 외부,64/64 내부, 미연결·중복0.
- 수용된 MUST의 검증 계획 연결률100%. 실제 테스트 통과율과는 구분.
- 독립 리뷰3/3 완료, 모든 제안에 수용/기각/보류 이유 기록.
- 필수 규범의 미해결 충돌·검증 불가 표현0; 차단/보류는 별도 공개.
- 구현 상태를 확인되지 않은 PASS로 채운 항목0.
- 명세→테스트→구현 backlog의 추적 가능성. 채택 요구의 개수 자체는 성공 지표로 삼지 않는다.

## Open Questions

- 숨김/aria-hidden 텍스트, 접근 이름과 textContent/innerText의 정확한 검색 의미는 아직 모두 확정한 계약이 아니다. 현재 동작과 사례를 구분해 명세화할 결정 대상이다.
- 비교 대상 Codex/Aside의 옵션별 지원 범위와 현재 실측 가능 여부는 수집 단계에서 다시 확인한다.
- 기존 카탈로그 밖의 노출 호출/별칭이 있으면 공개 API 여부를 먼저 결정한다.
- 실제 외부 사이트·회사 환경에서만 확인 가능한 조건은 접근 전까지 미검증으로 남긴다.

위 항목은 계획 착수를 막는 질문이 아니며 단계별 조사·결정으로 처리한다. 새로운 권한이나 사용자 선호가 실제로 필요할 때만 별도 질문한다.
