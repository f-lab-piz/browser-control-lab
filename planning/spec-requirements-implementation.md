# 요구사항 기반 구현·독립 리뷰·자동 머지 계획

현재 사용자 승인 범위는 **6단계 B02A 마무리까지**다. 기존 전체21단계 Goal은 중단되었고, B02B(7단계) 이후는 착수하지 않는다. 아래 전체 계획은 향후 참고용으로 보존한다.

2026-11-01. 사용자 승인: 전체 Goal 수행, 각 PR을 독립 리뷰하고 기준 충족 시 메인이 재확인 없이 머지한다. 이 승인은 본 저장소 요구사항 구현에 한정한다.

## Problem

기본 동작이 구현된 프로토타입과 새 요구사항의 충족 여부가 다르다. 185개 요구·254개 상세 사례를 실제 제품 경로로 확인하고 발견된 차이를 수정해야 한다. 문서 연결이나 기존 PASS로 새 요구를 충족했다고 처리할 수 없다.

## Target User

에이전트가 확장 안의 JavaScript 런타임에서 브라우저를 제어하는 사용자. 특히 중첩 iframe·큰 문서·가상 메뉴·격자 예약과 파일 전송 업무를 수행한다.

## User Value

검색과 스냅샷으로 대상을 발견하고 실제 입력·파일 전송까지 예측 가능한 계약으로 완료한다. 실패·부분 효과·미검증을 구분해 재시도로 인한 중복 변경을 줄인다.

## Use Cases

- 키워드를 모르는 페이지에서 영역→프레임→대상을 발견해 제어한다.
- 내부 스크롤로 메일137을 불러와 읽음 처리한다.
- 회의실 격자를 드래그·더블클릭하고 예약을 저장한다.
- 가상 메뉴230을 찾아 선택하고 로컬/server 파일을 업로드·다운로드한다.
- 실패·reset 이후 보존된 탭/파일을 관찰하고 새 세대 핸들로 계속한다.

## Corner Cases

타세션 소유·동일 ID 다른 payload·lexical 충돌·late hostcall·잘린 출력·문서 교체·중복 대상·가림·readonly·OOPIF·누적 clipping·MIME 충돌·이벤트 경쟁·완료 파일 취소를 해당 REQ의 조건별로 확인한다. scope.evaluate의 부작용은 원상복구를 주장하지 않는다.

### 매 PR 루프

1. main 동기화, 해당 issue 생성/갱신, 짧은 branch 생성. REQ/PLAN/Cnn 및 공통 계약을 읽는다.
2. 조건별 독립 준비와 판정기를 작성·보강하고 Before를 보존한다. fixture oracle과 제품 확장 경로를 별도로 기록한다.
3. 최소 공통 엔진 수정, guide/catalog/예제의 계약 일치. 새 의존성은 필요 근거를 남긴다.
4. 같은 seed·fixture·목표의 After, 오류·무부작용 또는 명시 부분 효과를 확인한다. 관련 단위와 실제 제품 경로, 기존 메일/예약/가상 메뉴 회귀를 수행한다.
5. Codex·Aside·우리 Before/After의 비교표를 만든다. 현재 실측·문서·과거 관측·환경 차단을 구분한다. 비교 환경 차단은 관련 참고 근거를 남기며 우리 제품 필수 테스트를 대체하지 않는다.
6. PR 생성/첨부, 정확한 base/head를 Sol6.1 high 새 컨텍스트 독립 리뷰에 전달한다. 리뷰어는 수정하지 않는다. 메인이 판단·수정하고 중요한 변경은 새 head로 재리뷰한다.
7. 아래 머지 gate를 확인해 메인이 머지한다. main 재동기화, issue·실행 로그·조건 상태를 갱신하고 다음 slice로 간다.

### 자동 머지 gate

- 포함한 MUST의 모든 상세 조건과 연관 회귀가 통과한다. 부분 조건 PASS는 부모 전체 PASS가 아니다.
- 실행 명령/종료 코드/브라우저·환경/seed·시각/코드 및 증거 hash를 기록한다. HTTP200·호출 성공만으로 판정하지 않는다.
- reviewer 판정 PASS, 미해결 P0/P1/P2 없음. 비차단 P3 보류는 영향·후속 담당 기록. INCOMPLETE와 실행 차단을 승인으로 처리하지 않는다.
- 테스트가 판정기를 우회하거나 기대 조건을 낮추지 않는다. 도구 계약·카탈로그·사용 예제와 실제 지원 범위가 일치한다.
- GitHub가 요구하는 checks를 통과하고 mergeable 상태다. 보호 규칙 우회/admin merge를 사용하지 않는다. base 변경 영향이 있으면 재검증·필요 재리뷰한다.
- 범위 밖 작업·배포·계정/개인 프로필 변경은 이번 자동 머지 승인에 포함하지 않는다.

조건 미충족 시 해당 PR은 계속 보완한다. 외부 연결·권한처럼 자율 해결 불가인 필수 차단은 근거와 재개 조건을 남기고, 실제 독립 작업만 계속한다. 횟수 소진을 이유로 PASS로 바꾸지 않는다.

## Cost and Complexity

기존 엔진과 fixture를 재사용한다. 모든 테스트 페이지를 먼저 재작성하는 대안보다 각 slice의 반례를 추가하는 방식이 작고 추적하기 쉽다. B01 세대/실행과 B03 문서/좌표, B05 이벤트 경쟁이 복잡도가 높아 단독 PR 경계를 유지한다. 근거 없는 일정·성능 수치를 약속하지 않는다.

## Usability

외부 guide/reset/js 세 개와 내부64 API를 유지한다. 구현 변화가 기존 예제와 충돌하면 변경 예제와 오류 의미를 함께 제공한다. 스냅샷은 긴 URL 나열보다 역할·이름·상태·ref·다음 탐색 수단을 보존한다.

## Risks and Mitigations

- 새 계약은 현재 코드와 다르다: 실패 재현 후 수정, 기존 테스트 변경 사유와 영향 기록.
- 문서 검사기는 과거 제품 동결 검사를 포함한다: 구현 시작 때 구조 검사와 과거 동결 재현을 분리하며 manifest는 보존한다. 동결 실패를 요구 위반으로 오해하지 않는다.
- 단위 PASS와 실제 확장 PASS의 차이: HTTP→확장→QuickJS 경로, 독립 DOM/파일 bytes/서버 판정을 필수 증거로 남긴다.
- 비교 도구 미접속: 수치 조작 없이 차단 상태/대체 문서/날짜 기록, 우리 필수 검증은 유지한다.
- 세부 상태 누락: 185 REQ/254 조건 담당 중복·누락을 구조 검사하고 조건별 증거를 연결한다.

## Decision

문서 PR과 계획 PR을 먼저 머지한다. 이후 B01A부터 21 slice를 순서대로 구현·검증·독립 리뷰·머지하며, 검증 결과에 따라 slice를 더 작게 나눌 수 있다. 순서는 선행 기반을 충족한 경우에만 조정하고 로그에 이유를 남긴다.

## MVP Scope

이번 수용 범위는 요구사항 정본의 MUST182와 SHOULD3이다. MUST는 완료 시 전부 충족한다. SHOULD는 구현 또는 비용/영향/판단과 잔여 제한을 기록한다. Chrome 외 어댑터, 전체 AX 표준, closed Shadow/canvas/PDF 의미 추출, 서비스 전용 도구와 상용 배포는 별도 범위다.

## Success Metrics

- 185개 부모 REQ·254개 상세 조건의 담당과 최종 상태 누락0.
- MUST182의 적용 상세 조건 전부 증거 있는 PASS, SHOULD3은 명시 처리.
- 메일137·격자 예약·메뉴230·파일 hash의 실제 제품 업무 판정 통과.

- 최종 요구사항 현황·제한·사용법 PR까지 머지. 조건 수와 API 수, 비교의 실측/미확인 수를 혼동하지 않는다.

## Open Questions

현재 개입이 필요한 질문은 없다. 구현 중 계약 충돌은 근거·대안·영향을 작성하고 기존 목표를 유지하는 쪽으로 자율 해결한다. 필수 요구를 제거하거나 범위를 크게 바꾸는 결정은 별도 기록하며 임의 완료 처리하지 않는다.

## 계획 PR 리뷰 보완

부모/조건의 pass·fail·blocked·deferred는 근거 참조가 필요하다. SHOULD 부모 보류는 하위 조건도 각각 보류 결정이 있어야 한다. slice는 not-started/in-progress/pass/blocked로 제한하고 시작/통과 시 선행 slice가 pass인지 검사한다. slice pass는 담당 부모 요구의 pass 또는 SHOULD deferred와 slice 자체 검증 근거를 요구한다. B04D처럼 부모를 중복 소유하지 않는 통합 slice도 자체 증거가 필요하다. 이 검사기는 상태의 구조·집계 일관성을 확인하며 증거 내용의 진실성·테스트 실행·독립 리뷰·GitHub checks는 메인의 머지 gate에서 별도 확인한다.
