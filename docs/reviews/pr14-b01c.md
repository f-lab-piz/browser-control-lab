# PR #14 독립 리뷰

## 발견 사항

### P2 — 압축 ICC 프로필이 PNG 디코딩 작업 공간 한도를 우회한다

- 위치: `extension/output.mjs:42` (`validateInflation`의 IDAT 전용 사전검사: 15, 25–27행).
- 발생 조건: 작은 1×1 PNG에 압축 `iCCP` chunk를 넣는다. 재현 입력은 파일 81,634 bytes, IHDR 1×1, 정상 IDAT 5 bytes이며 iCCP의 zlib 데이터가 83,886,080 bytes(80 MiB)로 확장된다.
- 기대: 공개 안내의 PNG 디코딩 작업 공간 64 MiB를 넘는 압축 메타데이터도 decoder 호출 전에 제한 오류로 종결해야 한다.
- 실제: 사전검사는 IDAT만 합쳐 제한한다. 이어 호출되는 fast-png 8.0.0의 `decodeiCCP` (`node_modules/fast-png/lib/png_decoder.js:323–333`)는 `unzlibSync(compressedProfile)`를 출력 한도 없이 호출한다. 직접 디코딩한 프로필 길이는 83,886,080 bytes였다. 실제 HTTP→확장→QuickJS 경로에서도 image 블록과 `icc-after`를 정상 반환하고 오류/잘림이 없다.
- 영향: QuickJS의 64 MiB 제한 밖인 호스트 decoder가 작은 이미지 입력으로 그 이상의 메모리를 할당한다. 더 큰 압축 프로필에서 브라우저 확장 프로세스의 메모리 고갈을 유발할 수 있다. 80 MiB 확장까지 실측했으며 실제 OOM/crash는 유발하지 않았다. 원래 base에는 decoder 호출 자체가 없어 이 추가 할당 경로는 이번 PR에서 도입됐다.
- 근거: `probe-png.mjs`, `probe-png.json`의 `ICC-inflate-over-64MiB`, `probe-product.mjs`, `probe-product.json`의 `product-ICC-over-64MiB`. 새 의존성의 압축 metadata 처리도 IDAT와 함께 예산 안에 넣어야 한다.

### P2 — 잘린 Adam7 PNG를 정상 이미지 블록으로 전달한다

- 위치: `extension/output.mjs:22–27`, 특히 27행.
- 발생 조건: 1×1 RGBA8, interlace=1 PNG의 IDAT를 `[0,12]` 두 bytes로 구성한다. 정상 데이터는 filter 1 byte + RGBA 4 bytes로 5 bytes여야 한다. PNG chunk CRC와 zlib checksum은 유효하다.
- 기대: `display`가 동기 `INVALID_IMAGE`를 던지고 이미지 블록은 추가하지 않아야 한다(REQ-DISPLAY-002-C01).
- 실제: interlace=1이면 `expected=null`이므로 27행에서 정확한 scanline 길이를 확인하지 않는다. fast-png의 Adam7 decoder도 짧은 scanline을 보완해 받아들이며, 직접 decode는 `[12,0,0,0]`을 만든다. 제품 경로는 67-byte PNG를 정상 image와 `accepted`, `after`로 반환한다. 동일 원바이트의 독립 Chromium `createImageBitmap` 판독은 `InvalidStateError: The source image could not be decoded.`로 실패한다.
- 영향: 모델에 실제로 표시할 수 없는 손상 이미지가 성공 응답에 포함되고 새 PNG 검증/완전한 이미지 전달 주장이 성립하지 않는다. base도 corrupt 입력을 허용했으므로 기존 누락을 이번 validator/조건 PASS가 아직 해소하지 못한 경우다.
- 근거: `probe-png.json`의 `interlaced-truncated`, `probe-product.json`의 `product-truncated` 및 `independent-native-oracle-truncated`. 재현 base64: `iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAFoEvQfAAAACklEQVR4nGPgAQAADgANC0koaQAAAABJRU5ErkJggg==`. Adam7의 실제 pass별 scanline 길이까지 확인해야 한다.

### P2 — 사용자가 던진 RangeError가 자원 고갈로 오분류되어 binding을 잃는다

- 위치: `extension/runtime-worker.mjs:50–51`.
- 발생 조건: 세션에서 `var preservedBinding=123;`을 실행한 다음 `throw new RangeError('out of memory')`를 실행한다. 실제 메모리 할당/고갈은 없다.
- 기대: 일반 사용자 예외는 `JS_ERROR`, `runtimeReset:false`이며 기존 binding/세대를 유지한다(공개 실행 한도 안내 및 REQ-C-RUNTIME-004-C01의 실제 자원 실패 구분).
- 실제: guest가 정할 수 있는 오류 `name`과 message만 보고 `RESOURCE_LIMIT`, reason `memory`, `runtimeReset:true`를 반환한다. 다음 요청은 generation 1→2이고 `typeof preservedBinding`은 `undefined`다. 기존 일반 Error('out of memory') 테스트만으로는 이 경우를 발견하지 못한다.
- 영향: 통상 사용자 예외를 실제 VM 고갈로 오인해 불필요하게 전체 세션 변수를 제거한다. 해당 분류/자동 reset은 이번 PR에서 도입됐다.
- 근거: `probe-product.json`의 `user-RangeError-is-not-resource-exhaustion`. 자원 고갈의 실제 엔진 상태/출처와 사용자 예외를 구분해야 한다.

P0/P1 발견 사항은 없다. 위 3개는 가설이 아니라 현재 head의 실제 제품 경로와 연결 코드로 확인했다. 요구사항 ledger의 6부모/7조건 PASS는 위 미충족 경계를 보완한 후 다시 판단해야 한다.

## 검증/재현 명령 및 결과

실행 환경: Node v25.2.1, Python 3.14.2, 프로젝트 helper가 기동한 Chrome for Testing 전용 임시 프로필. 최초 원본 HEAD는 지정 head와 일치했고 `git status --short` 출력은 없었다. 원본 제품/테스트/문서는 수정하지 않았다.

검증 사본은 이 보고서와 같은 ignored 디렉터리의 `exact-source/`다. 지정 head를 shared clone한 후 기존 node_modules를 링크했다. 최초 실행의 dirty=true는 추적되지 않은 node_modules 심볼릭 링크 하나 때문이었고, 검증 사본 `.git/info/exclude`에 링크를 제외한 뒤 clean 상태로 `test:all`/headed 전체를 다시 통과했다. 어떤 tracked 소스도 달라지지 않았다. 전체 제품 테스트에서 입력은 HTTP→확장→세션별 QuickJS를 사용한다.

`test:all` 구성 집계는 unit 24, fixture oracle 8, bootstrap 1, 기존 제품 24(+외부1 SKIP), 요구 제품15, 기존 경계7이다. Fixture UI/PNG native oracle 및 fake-extension 전송 단위는 제품 PASS로 합산하지 않고 별도 등급으로 해석했다. 추가 반례의 Playwright 판독은 잘린 PNG의 native decode oracle일 뿐이며, 제품의 display 호출은 HTTP→확장→QuickJS였다.

통제 Before도 `before-source/`에서 독립 재현했다. 현재 테스트/fixture/의존성/문서/helper/새 output 및 limits를 고정하고 `bridge/server.mjs`, `extension/runtime-worker.mjs` 두 파일만 정확 base로 교체했다. 이는 전체 과거 환경 재현이 아니다.

- `BCL_RUN_DIR=../before-product node --test tests/output-runtime.test.mjs`: exit 1, 1 PASS / 5 FAIL (`before-product.log`).
- `node --test tests/output-transport.test.mjs`: exit 1, 0 PASS / 2 FAIL (`before-transport.log`).
- 현재 head의 대응 제품6개와 전송2개는 전체 회귀에서 통과했다.

증거/문서 독립 확인:

- `docs/evidence/b01c/manifest.json`의 15개 전달 파일 SHA와 원시 source SHA가 모두 일치한다(`manifest-audit.json`).
- 기록된 Before/After source hash 차이는 주장대로 server/worker 두 파일뿐이다. After의 모든 기록 소스 SHA가 현재 head 파일과 일치한다. 기록 자체의 git head는 양쪽 base/dirty=true지만, 문서가 통제 비교임을 분명히 표시하고 파일 hash가 실제 소스를 특정하므로 정확 head 실행으로 오인하지 않았다.
- 경쟁 도구 자료는 Codex 수신 출력 전사(원본 자동 export 아님), Aside CLI stdout/exit 캡처로 명시되어 있다. bounded console LIVE와 기타 이미지/예산/전송 미측정이 구분되고 출력 글자 수의 성능 우위를 주장하지 않는다. 기존 DOC/HISTORICAL과도 분리되어 있다.
- 변경 의존성/빌드 경로는 공개 범용 fast-png/fflate와 기존 QuickJS를 사용한다. 경쟁 제품 원본/번들/WASM 추가는 diff에서 발견하지 않았다. 개인 로컬 loopback 전송과 세션 격리를 다중 사용자 계정 보안으로 확대 해석하지 않았다.

## 미실행/차단

- 외부 사이트 테스트 1개는 기존 조건대로 SKIP했다. 외부/회사 사이트 전체 동작은 검증하지 않았다.
- 경쟁 Codex/Aside LIVE 실행을 이번 리뷰에서 새로 수행하지 않았다. 저장된 artifact/provenance/범위와 hash만 확인했다. 전사만으로 경쟁 실행 당시의 원본 tool payload를 독립 복구할 수 없다.
- ICC 압축 폭탄의 80 MiB 초과 확장은 검증했지만, 더 큰 할당으로 실제 OOM/브라우저 crash를 유발하지 않았다.
- B01D/B01E/B02~B06 및 185개 전체 요구의 제품 적합성은 이 리뷰 범위 밖이다. 검사기 PASS는 문서/계획 구조 결과다.

## 잔여 위험

PNG decoder가 처리하는 모든 ancillary/압축 chunk와 Adam7 scanline 구조가 현재 단위 테스트의 noninterlaced 1×1 fixture보다 넓다. 두 PNG 반례를 회귀로 추가하고 decoder 전체 자원 사용을 다시 확인해야 한다. 오류 분류도 공개 오류 이름/문구만으로 실제 엔진 고갈을 확정하면 사용자 예외에 의한 불필요한 세대 reset이 남는다.

소유한 테스트 프로필/브라우저/fixture/bridge는 helper가 종료했다. 원격 PR 댓글·리뷰·승인·머지는 수행하지 않았다. 최종 원본/검증 사본 SHA는 그대로이며 원본 tracked 변경은 없다.
