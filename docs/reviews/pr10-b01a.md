# PR #10 B01A 독립 리뷰

## 발견 사항

### P2 — 허용한 requestId 문자열을 결과 조회 URL에서 왕복하지 못함

- 위치: `bridge/server.mjs:63-64` (이번 PR의 식별자 접수 검증), `bridge/server.mjs:54-55` (결과 경로 조회), `bridge/client.mjs:3` (ID를 URL에 그대로 연결). 새 계약은 `docs/runtime-usage.md:72`에 명시되어 있다.
- 연결 요구/조건: `REQ-C-RUNTIME-005-C01`, `REQ-JS-002-C02`; external/js의 입력 계약은 `requestId?:string`, 성공 의미는 조회 가능한 실행 상태·출력·오류다. 이번 B01A는 요청 식별·접수 검증을 담당하며 비어 있지 않은 문자열을 허용한다고 안내한다.
- 발생 조건: `requestId`가 `job/a`, `한글`, `job?part`, `job#part` 같은 비어 있지 않은 문자열이면 POST는 HTTP 202로 접수하고 확장 QuickJS에서 정상 실행한다. 그러나 결과를 `GET /v1/requests/<id>`로 조회하면 raw/`encodeURIComponent(id)` 양쪽 모두 404다. 클라이언트는 ID를 인코딩하지 않으며 서버도 경로 조각을 디코딩하지 않는다.
- 기대/실제: 허용한 ID는 해당 요청의 종결 상태·결과로 조회되어야 한다. 실제로는 이미 수행한 코드의 결과가 조회 불가능하다. 더 나아가 먼저 ID `job`으로 `console.log("first-output")`를 완료한 후 ID `job#part`로 `console.log("second-output")`를 호출하면 `client.js`는 기존 ID `job`의 `first-output`을 반환한다. 실제 `job#part`는 별도로 실행 완료되어 `second-output`을 생성했다. ID가 다른 요청의 결과로 조용히 바뀐다.
- 사용자 영향: 완료 여부를 판단하지 못하거나 다른 요청의 성공/출력을 자신의 결과로 오인한다. 비멱등 조작에서 완료 확인과 안전한 재시도 판단을 훼손한다.
- 증거: `output/review-b01a/request-id.json`, `request-id-runtime/results.json`, `request-id-collision.json`, `request-id-collision-runtime/results.json`. 모두 실제 HTTP → 확장 → QuickJS 경로이며 Playwright는 기동/독립 판독만 담당했다. 재현 스크립트는 `.local/goal-development/review-b01a/request-id.mjs`, `request-id-collision.mjs`다.
- 도입 여부: URL 연결/조회 경로는 base에도 존재한 결함이다. 이번 PR에서 새로 도입한 회귀로 주장하지 않는다. 다만 이 PR이 입력 검증·문서화하고 PASS로 올리는 B01A 요청 식별 계약의 잔여 결함이므로 수용 전 보완이 필요하다. 클라이언트 인코딩+서버 디코딩으로 허용 문자열을 보존하거나, 실행 전에 일관된 안전 형식으로 제한하고 계약을 맞춰야 한다.

그 밖에 B01A 실제 diff와 연결 요구 범위에서 확정된 P0/P1/P2 발견 사항은 없다. 인증 토큰은 개인의 모든 대화 세션을 관리하는 로컬 관리 자격이라는 사용자 확인을 적용했다. 다중 사용자 서비스 인증·계정 격리를 추가 요구하지 않았다.

## 미실행/차단

- 독립 리뷰에서 HEADED=1 테스트는 재실행하지 않았다. 저자의 headed4/4 원시 결과는 현재 source hash 일치까지 확인했다.
- 외부 Naver 시나리오 1건은 기본 설정으로 SKIP이며 외부/회사 사이트 성공을 주장하지 않는다.
- 이번 검토에서 경쟁 Codex/Aside 신규 실측은 수행하지 않았다. PR 비교표는 문서/미확인/미측정을 구분하고 성능 우위를 주장하지 않는다.
- Before 제품/단위 테스트는 독립 checkout에서 다시 실행하지 않았다. 기존 원시 Before/After 로그·manifest·소스 해시와 테스트 assertion을 검토했으며 After/추가 반례는 직접 실행했다.
- 원격 리뷰 게시·승인·머지는 수행하지 않았다.

## 남은 위험

- 최초 전체 회귀에서 관측된 중첩 프레임 불안정은 순차 재실행에서 재현되지 않았다. 프레임 동작의 새 결함으로 확정할 증거가 없으며 기존 복합 시나리오의 일시 실패 기록은 남긴다.

## 메인 판단

P2 요청 ID 결과 조회 결함을 수용했다. 단순 URI-safe ID 제한 대신 한글/예약문자/`.`/`..`/NUL을 데이터로 유지하는 query 조회를 client 기본으로 사용하고 기존 경로에도 URI decoding을 적용한다. 잘못 짝지어진 surrogate는 접수 전 거절한다. 고정 job과 job#part를 동시에 준비해 잘못된 prefix 결과를 읽는 반례와14개 식별자의 단위·12개 실제 제품 왕복을 추가한다. 최초 프레임 회귀3건 실패와 순차55 PASS/1 SKIP를 함께 보존하며 이를 신규 B01A 성공으로 덮지 않는다. 보완 후 순차 전체 회귀와 새 head 독립 재리뷰를 진행한다.
