# 요구사항별 참고 방식 · 실행 기록

제품 기준700a6a0, 문서 조사 시작8503267, 2026-11-01. 외부3/내부64 API와 공통5문서의184개 요구를 기준으로 한다. 기존 규범을 독립 판정 가능한 구체 사례로 상세화하고, 참고 방식은 이 디렉터리에서 따로 관리한다.

읽는 순서: [요구별 양쪽 연결](index.json) → 배치별 참고 본문 → [주장/근거](evidence-index.json) → [판단](decisions.md) → [집계](coverage.json). 원래 요구의 각 REQ에는 해당 참고 본문 링크가 있다. 정본 상세조건은 [condition index](../condition-index.json)에서 찾는다.

## 데이터 해석

- `direct/composition/unknown`은 API 사용 방법의 대응 관계다. direct도 전체 요구의 동등 지원을 뜻하지 않는다.
- 각 주장에는 DOC/LIVE/HISTORICAL/INFERENCE가 붙는다. 문서 서명, 과거 한 fixture 관측, 새 실측, 우리 설계 추론을 섞지 않는다.
- condition의 `not-established`는 그 조건 전체의 동등성을 증명하지 않았다는 뜻이다. 미지원이라는 뜻이 아니다. `relatedClaims`는 조사 단서이며 충족 증거로 집계하지 않는다.
- 호출 조각은 공개 문법을 확인한 미실행 예제다. null syntax인 항목은 API 이름을 발명하지 않고 공백·후속 확인 방법을 남긴다. 전체 순서 예제는 각 제품 evidence/sources.md의 실행/미실행 구분을 확인한다.
- Codex 주 표면은 CUA/IAB, Aside는 원본CLI1.26.1028.2335/skill3이다. 자체 wrapper나 일반 Playwright와 동등하지 않다. 다른 어댑터의 보충 관측은 주 표면에 합산하지 않는다.
- 공개 문서에서 내부 구현 알고리즘을 추출했다고 주장하지 않는다. 원본 구현 코드·번들·제품WASM·사용자 프로필은 수집하지 않는다.

## 집계

연결률은184×2 슬롯, 조건 근거 확인률은 condition-index의 고정 조건×두 주표면 단위다. DOC/LIVE/HISTORICAL은 해당 조건 전체를 뒷받침한 경우만 확인 분자에 넣고 부분 자료는 relatedClaims에 남긴다. source/claim/run의 고유 수는 별도 중복 제거한다. 문서 목록을 많이 채웠다는 이유로 확인률을 올리지 않는다.

우리 상세조건에는 세션·asset·timeout·예산·부분실패 등 독립 정책이 많다. 공개 안내에 동등 계약이 없으면 근거 확인률이 낮을 수 있다. 이 경우 우리 사용자 요구/반례/검증계획으로 설계를 판단하고 부족한 실측은 개발 backlog에 남긴다. 문서 루프 완료와 제품 구현/적합성은 다르다.

## 상세화의 근거

정상 조건·잘못된 입력·중간 상태변화·부분효과의 준비/실행/판정식을 작성했다. click의2프레임/1px·5초 actionability 등 수치는 **우리 설계 결정**이며 경쟁 제품의 내부 알고리즘을 주장하지 않는다. 상위 요구와 새 상세조건이 충돌하면 메인이 판정하고 변경 이력을 남긴다. 기존184개를 모두 새 요구로 재번호화하지 않는다.
