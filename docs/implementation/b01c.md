# B01C: 출력·이미지·실행·전송 예산

요청별 공통 출력 버퍼를 추가해 텍스트·이미지·블록을 분리 계산한다. console의 NUL/Unicode와 순환 표지를 보존하고, PNG는 파일 구조·CRC·scanline·zlib checksum을 검사한 뒤 완전한 이미지로만 전달한다. 실제 호스트 스택 중단은 RESOURCE_LIMIT와 새 generation으로 구분하고, guest 예외는 이름/문구로 VM을 초기화하지 않는다. 보완된 새 head의 독립 리뷰 전이며 slice는 in-progress다.

## PNG·자원 구현과 검증 등급

PNG fixture는1×1 RGBA 픽셀과 정확한 파일 길이의 ancillary tEXt chunk로 구성한다. 독립 Chromium의 createImageBitmap/canvas oracle에서128 bytes·4MiB±1/정확 경계의 실제 픽셀[12,34,56,255]를 확인했다. 이 oracle은 제품 PASS와 구분한다.

PNG 색상별 bit depth·PLTE 크기/순서/필수 여부·tRNS·CRC·scanline·Adler checksum을 자체 행 스트리밍 검사기로 확인한다. [PNG 표준 Adam7 7개 pass](https://www.w3.org/TR/png-3/#8InterlaceMethods)의 행 길이를 계산하며, indexed는 두 행 버퍼로 Sub/Up/Average/Paeth 필터를 복원해 실제 palette index를 검증한다. pako3.0.3의 Inflate를 사용하며256bytes 입력 조각과 고정64KiB 출력 조각으로 처리한다. zlib-only windowBits15·DEFLATE 구조·checksum·스트림 종결/전체 입력 소비를 확인하고 출력 callback에서 예산 초과 즉시 중단한다. 전체 raster나 palette 배열은 펼치지 않고 IDAT도 파일 길이 이내 단일 버퍼로 모아 chunk 수에 비례한 view 누적을 막는다. 파일 사본·inflate 여유·행 버퍼의 보수적 작업 공간과 확장 데이터는 각각64MiB 이내여야 한다. ICC·zTXt·iTXt 압축도 제한 스트림을 사용하고 반환 원본 PNG bytes는 유지한다. 과도한 확장은 IMAGE_RESOURCE_LIMIT로 구분한다.

초기 fast-png8.0.0 decoder는 잘못된 형식을 수용하고 정상 저비트 Adam7/RGB transparency를 거절하는 반례가 확인되어 제품 의존성에서 제거했다. W3C 형식 규칙을 참고해 자체 행 검사를 작성했으며 경쟁 제품 코드/WASM을 사용하지 않았다. 과거 Before 재현에 필요한 당시 decoder 패키지는 ignored scratch에만 있다. 66개 corpus(정상40·잘못된 형식/자원 초과26)를 실제 display에서 모두 판정한다. 독립 native oracle은 지원 조합과 필터별 픽셀을 확인한다. Chromium이 일부 비표준 구조를 관대하게 수용하는 사실과 우리 구조/자원 제한은 구분하며 PNG 표준 전체 적합성을 주장하지 않는다.

guest 예외 이름/문구는 사용자가 위조할 수 있어 원인을 증명하지 않는다. QuickJS가 반환한 실제 메모리 한도 InternalError도 JS_ERROR/guestName으로 보고하고 VM이 유지되면 runtimeReset:false다. 이 설계는 정본의 VM 실제 재생성 여부를 명시하라는 계약을 따른다. 메모리 예외마다 재생성해야 한다는 추가 가정은 제거했고 실제 한도·복구와 일반 예외의 상태 보존을 더 검증했다. 물리 스택 RangeError는 VM 재사용을 시도하지 않고 종료한다. 자원 실패 결과가 runtimeReset:true일 때 기존 offscreen 수명 경로가 VM을 제거하고 중계기가 generation을 갱신한다. B01D의 전체 late hostcall·입력 release 충족을 대신하지 않는다.

## 두 번째 독립 리뷰의 보완

최신 final4 전체 회귀는83 PASS/외부1 SKIP이고 최종 제품 소스 hash가 모두 일치한다. 같은 최종 코드의 직전 final2 전체 실행에서 다운로드 취소 TIMEOUT1건으로 종료한 사실은 별도 raw 실패로 보존한다. 다른 테스트와 겹치지 않은 final4 재실행에서 해당 취소도 통과했으나 간헐 원인은 미확정이며 독립 리뷰에서 재검증한다. 현재 PNG 처리와 무관하다는 인과 주장을 하지 않는다. 새 head의 독립 판정과 머지는 여전히 필요하다.

## 세 번째 독립 리뷰의 보완

정확64f2de4의 [Sol6.1 high 리뷰](../reviews/pr14-b01c-round3.md)는 P2 한 건으로 CHANGES_REQUESTED였다. CRC/Adler/scanline은 맞지만 DEFLATE stored block의 LEN/NLEN 보수값이 틀린73bytes PNG를 fflate가 받아 실제 display도 성공 이미지로 반환했다. 독립 Chromium과 Node zlib는 거절한다. 리뷰 원시 정상 대조/반례를 보존한다.

범용 압축 검증기를 pako3.0.3(MIT AND Zlib)로 교체하고 fflate는 제품에서 제거했다. [공개 Inflate API](https://nodeca.github.io/pako/classes/Inflate.html)의 onStart/onData·ended/err와 스트림 입력 소모를 사용하며 출력 조각64KiB 이상을 통째로 누적하지 않는다. 최대 해제량에서 즉시 예외를 던져 기존 자원 거절을 유지한다. 자체 DEFLATE parser나 경쟁 제품 코드를 복사하지 않았다.

추가8개 압축 사례는 정상 stored/fixed/dynamic 세 종류와 손상 LEN/NLEN·잘린 stored·header·Adler·압축 metadata다. 실제 display/catch/후속 log에서 판정하며 입력1회로 다른 사례 통과를 대신하지 않는다. 독립 native oracle은 stored LEN/NLEN·truncated/header를 거절하지만 손상 Adler와 ancillary metadata는 관대하게 표시한다. 이 관찰은 제품의 명시 형식 오류 요구를 낮추지 않는다. 첫 native 기대값 오류 실행도 원시 이력으로 보존하고 실제 브라우저 동작과 제품 규범의 차이를 기록한다.
